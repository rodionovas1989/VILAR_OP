## Авторизация и аудит

| # | Задача | Статус |
|---|--------|--------|
| A1 | Шапка: активный пользователь, Войти/Выйти | в работе |
| A2 | JWT + «Запомнить на этом компьютере» (localStorage) | в работе |

| A4 | Права доступа по ролям (RBAC) | отложено |

| A6 | Переход на httpOnly cookie + refresh token (прод) | идея |

### Варианты «запомнить авторизацию» (справочно)

| Подход | Как работает | Плюсы | Минусы |
|--------|--------------|-------|--------|
| **JWT в localStorage** | Токен после входа; «Запомнить» → localStorage, иначе sessionStorage | Просто, без серверных сессий | XSS может украсть токен |
| **httpOnly cookie** | Сервер ставит cookie, JS не видит | Безопаснее от XSS | Нужен CSRF, сложнее SPA |
| **Refresh + access token** | Короткий access + долгий refresh в cookie/storage | Баланс безопасности | Больше кода |
| **ОС / браузер (SSO)** | Windows AD, Keycloak | Корпоративный стандарт | Инфраструктура |

**Текущий выбор (v1):** signed JWT в localStorage (30 дней) или sessionStorage (сессия браузера).

## Документы — целевая архитектура

> Решение: **не один** универсальный документ, а **отдельная сущность на тип** с собственной вкладкой и правами.

| Вкладка навигации | Коллекция (план) | Код |
|-------------------|------------------|-----|
| Приёмка | `receipt_documents` | RCP |
| Перемещение | `transfer_documents` | TRN |
| Инвентаризация | `inventory_documents` | INV |
| Списание | `writeoff_documents` | WOF |
| Оприходование | `posting_documents` | PST |
| Резервирование | `reservation_documents` | RES |
| Списание в производство | `production_issue_documents` | PRI |
| Выпуск из производства | `production_receipt_documents` | PRR |
| Отгрузка | `shipment_documents` | SHP |

Общий каркас (статусы, нумерация, post/cancel) — **общий сервис**, данные — **раздельные коллекции**.

Миграция: текущий `stock_documents` → разнести по типам на этапе 2.

### Обсуждение идеи

**Суть:** персональная стартовая страница вместо фиксированного «Рабочего стола планирования».

**Модель данных (черновик):**
```json
{
  "userId": "user-admin",
  "items": [
    { "id": "planning_desktop", "kind": "desktop", "label": "Рабочий стол планирования" },
    { "id": "receipt_documents", "kind": "document", "label": "Приёмка" },
    { "id": "materials", "kind": "dictionary", "label": "Материалы" }
  ]
}
```

**Группировка на UI:** секции «Рабочие столы», «Документы», «Справочники», «Регистры».

**Добавление в избранное:** кнопка «☆» на странице объекта или пункт в контекстном меню навигации.

**Риски:** дублирование навигации (боковое меню + главная) — решается тем, что главная **сокращает путь** для частых задач, а полное меню остаётся.

**Рекомендация:** стабильные `pageId` уже в `navConfig.ts`; избранное привязано к ним.

## Заказ на производство vs складской документ

**Суть:** заказ — **управляющий документ** (оркестратор), а не документ движения запасов.

| | Складской документ (RCP, RES, …) | Заказ на производство |
|---|----------------------------------|------------------------|
| Коллекция | `*_documents` | `production_orders` (отдельно) |
| Табличная часть | строки материал/партия/кол-во | подбор сырья (`lines[]`), но это **план**, не проводка |
| Проведение | меняет остатки / регистры | **не проводит**; меняет статус и **создаёт** RES / PRI / PRR |
| UI | `DocumentTypePage` | та же **оболочка**, другой body |

**Рекомендуемая архитектура (не смешивать типы в `documents.js`):**

1. **Backend:** `services/productionOrders.js` — CRUD, статусы (`новый` → `спланирован` → …), переходы вызывают `documents.create/post` для RES/PRI/PRR.
2. **Ссылки:** на заказе хранить `reservationDocumentId`, `issueDocumentId`, … (id + number), не дублировать движения.
3. **Frontend:** `ProductionOrderPage` — список + модалка как у документов (шапка, badge статуса, «Действия», ☆); тело формы — реквизиты заказа + блок «Связанные документы» / подбор сырья (read-only после планирования).
4. **Общий слой UI:** вынести `DocumentShell` / переиспользовать `Modal` + `ActionsMenu` + `PageTitle` (без наследования от `DocumentTypePage` со строками TЧ).

**Рабочий стол планирования** остаётся массовым сценарием (много заказов); карточка заказа — детальный просмотр/редактирование одного заказа в стиле документа.
