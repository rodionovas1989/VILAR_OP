# Безопасность: публичная ВМ (пилот)

Контекст: пилот на Yandex Cloud, URL вида `http://IP:3001`, сервис `vilar-op`, SQLite на диске ВМ.

## Текущая оценка (открытый доступ по HTTP)

### Что уже защищает данные

| Мера | Статус |
|------|--------|
| API без токена (кроме `/health`, login, logout) | есть |
| RBAC на коллекциях/документах | есть |
| Пароли: scrypt + timing-safe compare | есть |
| Единое сообщение «Неверный логин или пароль» | есть |
| CORS allowlist (`CORS_ORIGIN`) | есть |
| Секрет токена: `AUTH_SECRET` / файл `auth_secret` | есть |
| Подсказок Admin/пароля в UI | нет |
| Гостевой UI: только форма входа (после `feature/auth-gate-landing`) | да |

Данные справочников и документов **не отдаются** без Bearer-токена. Это не «открытая БД в браузере».

### Реальные риски при публикации IP в интернет

| Риск | Почему важно | Критичность |
|------|----------------|-------------|
| **HTTP без TLS** | Токен и пароль идут открытым текстом; на чужой сети возможны перехват и подмена | **высокая** |
| **Порт 3001 наружу** | Любой в интернете видит UI и может бить `/api/auth/login` | высокая |
| **Нет rate limit на login** | Перебор паролей (особенно слабых учёток) | высокая |
| **Токен в localStorage / sessionStorage** | XSS → кража сессии; нет httpOnly cookie | средняя |
| **Нет Helmet / security headers** | Слабее защита от XSS/clickjacking | средняя |
| **SQLite + бэкапы на той же ВМ** | Компрометация ОС = компрометация данных и истории | высокая |
| **SSH с паролем/слабым ключом** | Обход приложения целиком | высокая |
| **Раскрытие факта пилота** | Health `{"ok":true}`, заголовок после входа, структура API | низкая (информация) |
| **Admin с сильным паролем** | Если пароль слабый или утёк — полный доступ | зависит от пароля |

**Вывод:** для закрытого LAN / VPN пилот приемлем. Для **открытого интернета по HTTP** — это осознанный риск пилота, не production-ready контур. Данные за auth, но транспорт и периметр слабые.

## План мероприятий, если заказчик остаётся на ВМ

Приоритет: сначала закрыть периметр и TLS, потом усилить приложение и процессы.

### Этап A — срочно (1–3 дня)

1. **Не оставлять 3001 в открытом 0.0.0.0 без фильтра**  
   Security Group / firewall: только IP офиса заказчика (или VPN-шлюз). Временно — ваш IP для администрирования.
2. **HTTPS**  
   Nginx (или Caddy) reverse proxy + Let’s Encrypt (или корпоративный сертификат). Приложение слушает `127.0.0.1:3001`, наружу только 443.
3. **Сильный Admin и отдельные учётки**  
   Уникальные пароли ≥12–16, без общих «рабочих» паролей; убрать лишних пользователей.
4. **SSH только по ключу**, отключить парольный вход; ограничить SSH по IP.
5. **Бэкап sqlite вне ВМ**  
   Ежедневно копировать `vilar.sqlite` (+ wal при остановке или после checkpoint) в объектное хранилище / второй контур. Проверить восстановление.

### Этап B — усиление приложения (1–2 недели)

6. **Rate limit** на `POST /api/auth/login` (например 5–10 попыток / IP / 15 мин) + опционально lockout учётки.
7. **Helmet** (или эквивалент заголовков): CSP, `X-Frame-Options`, `Referrer-Policy`, HSTS после HTTPS.
8. **Сессии:** переход на httpOnly Secure cookie (+ короткий access / refresh) вместо долгого токена в `localStorage` (особенно «запомнить»).
9. **Журнал входа:** успех/неуспех login (время, IP, login) — хотя бы в файл/syslog.
10. **Запрет индексации** (`noindex` уже на стартовой HTML) + не светить лишнее в `/api/health` (без версий/путей).

### Этап C — эксплуатация ВМ

11. Автообновления безопасности ОС (unattended-upgrades) или регламент патчей.
12. Мониторинг: `systemctl`, диск, неудачные SSH/login.
13. Регламент обновления кода: только с `main`, бэкап до деплоя, без `npm run seed` на бою.
14. Разделение ролей: кто админ ВМ ≠ кто Admin в приложении (по возможности).
15. План инцидента: смена `AUTH_SECRET` (инвалидация токенов), смена паролей, откат sqlite из внешнего бэкапа.

### Этап D — если вырастет нагрузка / требования ИБ

16. VPN (WireGuard / корпоративный) вместо «белого списка IP» вручную.
17. Вынести БД (Postgres) и бэкапы с app-сервера.
18. WAF / fail2ban на nginx.
19. Внешний пентест / аудит по чеклисту заказчика (152-ФЗ / внутренние политики — по их зоне ответственности).

## Сравнение: ВМ в облаке vs локально у заказчика

| | Облачная ВМ (публичный IP) | Локально / LAN заказчика |
|--|---------------------------|---------------------------|
| Угроза из интернета | высокая без SG+HTTPS | низкая (если нет проброса портов) |
| Перехват пароля | критичен без TLS | ниже в доверенной LAN, TLS всё равно желателен |
| Бэкапы | нужны вне ВМ обязательно | лента/NAS/регламент IT заказчика |
| Кто отвечает за периметр | вы + облако + заказчик | IT заказчика |

Рекомендация для пилота на ВМ: **этап A обязателен** до расширения круга пользователей. Этапы B–C — до «боевого» режима на той же ВМ.
