# Анализ: единицы измерения (UOM)

Статус: разбор + **есть план** [`docs/plans/uom-units-of-measure.md`](../../docs/plans/uom-units-of-measure.md). ROADMAP: **G12**. Обновлено: 2026-11-02.

**Зафиксировано:**

1. Базовая (**учётная**) ЕИ — на **карточке материала** (`baseUomId`), не в модели учёта.
2. **Одна учётная ЕИ:** все движения и регистры — только в ней.
3. Другие ЕИ + коэффициенты — **не исключены**, но как слой показа/ввода/отчётов (альтернативы), не как второй остаток.

## Сейчас

- У материала поле `unit` — **свободная строка** (`кг` / `уп` в seed); справочника ЕИ нет.
- В регистрах запасов, строках документов, резервах — только число `quantity` **без** единицы.
- Спека: норма `qtyPerUnit` концептуально **кг на 1000 уп** ([lot-recalc-assay-dry](../concepts/lot-recalc-assay-dry.md)); пересчёт assay/dry — весовой.
- UI: `unit` — подпись рядом с числом; точность — `qtyDisplayDecimals` модели учёта, не ЕИ.
- Характеристики LCH (`%` и т.п.) — **другой контур**, сюда не смешивать.

Инвариант сегодня: «все количества материала сопоставимы как одно число» — работает, пока у материала одна подразумеваемая ЕИ и нет переводов.

## Зачем менять

1. Учёт не только в кг (шт, л, г, т, уп разных фасовок).
2. Ввод/просмотр в удобной ЕИ с **автопересчётом** (1000 г ↔ 1 кг; упаковка ↔ кг по коэффициенту).
3. Явная база нормы в спеке (не «все знают, что кг/1000 уп»).
4. Позже — обмен с 1С/ERP (INT1), где ЕИ обязательны.

## Ключевые решения (независимо от варианта)

| Вопрос | Рекомендация по умолчанию |
|--------|---------------------------|
| Где истина остатка? | Всегда **базовая ЕИ материала** в регистрах и проводках |
| Можно ли менять базовую ЕИ материала с движениями? | Нет (или только миграция админом с пересчётом) |
| Автоперевод без коэффициента материала | Только **внутри размерности** (масса: кг↔г↔т; объём: л↔мл) |
| шт ↔ кг (фиксировано) | Коэффициент на **материале** (фасовка) |
| шт ↔ кг (плавающий вес) | См. [catch weight](#шт--кг-с-плавающим-весом-catch-weight); не материалный factor alone |
| Строка документа | Хранить `qtyBase` (обязательно); опционально `qtyEntry` + `uomEntry` для UX |
| Спека | Явные `normUom` + `perQty`/`perUom` вместо жёсткого «кг/1000 уп» |
| LCH `%` | Не в каталоге складских ЕИ |

## Варианты архитектуры

### A. Базовая ЕИ материала + каталог + альтернативы (классика ERP)

- Справочник `uoms`: код, имя, размерность (`mass` / `volume` / `count` / …), флаг системной.
- У материала `baseUomId`; остатки/проводки **только** в базе.
- Альтернативы материала: `altUomId` + `factorToBase` (сколько базы в 1 альт.).
- Внутри размерности — таблица системных факторов к эталону размерности (кг, л, шт); UI пересчитывает без записи фактора на каждый материал.
- Ввод: пользователь выбирает ЕИ → в регистр уходит qty в базе.

**Плюсы:** целостность запасов; простой FEFO/резерв/отчёты; понятно GMP («одна цифра остатка»).  
**Минусы:** нельзя провести документ «в чужой ЕИ» без перевода в базу; смена базы — боль.

**Оценка для Vilar:** **основной кандидат.**

### B. Двойное хранение в строке документа (entry + base)

Как A, плюс в каждой строке документа явно:

- `quantity` / `uomId` — как ввёл пользователь;
- `quantityBase` — канон для проводки.

Регистры по-прежнему только base.

**Плюсы:** аудит «что видел оператор»; удобно при приёмке в г при базе кг.  
**Минусы:** дубль полей, риск рассинхрона при смене фактора после черновика (нужен snapshot фактора на момент проведения).

**Оценка:** разумное **уточнение A** на этапе документов, не отдельная модель учёта.

### C. Только размерности + системные переводы (без альт. на материале)

Каталог ЕИ с размерностью; авто кг↔г↔т; на материале только `baseUomId`.  
Нет шт↔кг, пока не заведут отдельный материал или не расширят модель.

**Плюсы:** минимальный объём работ; закрывает «весовые пересчёты».  
**Минусы:** не закрывает фасовки/штучный учёт сырья, которое списывают в кг.

**Оценка:** хороший **MVP-срез A** (фаза 1), если ближайшая боль — граммы/тонны.

### D. Иерархия упаковок (паллета → короб → шт → кг)

Многоуровневые коэффициенты, SSCC/ТСД.

**Плюсы:** складская логистика.  
**Минусы:** избыточно до INT3/ячеек; не нужно для текущего ОП.

**Оценка:** **не сейчас**; не смешивать с G12.

### E. Свободный текст + таблица «перевод если захотим»

Оставить `unit: string`, кое-где хардкод переводов.

**Плюсы:** дёшево на вид.  
**Минусы:** нет контроля сопоставимости, ломает отчёты и GMP-след, плохо стыкуется с 1С.

**Оценка:** **отклонить.**

## Связь с уже существующим

| Место | Влияние |
|-------|---------|
| Спека `qtyPerUnit` / G7 assay-dry | Норма и пересчёт должны жить в **массовой** (или явно заданной) базе; «1000 уп» — `perUom` продукта |
| Заказ `quantity` (выпуск) | ЕИ продукта (сейчас «уп») |
| PRI/PRR/RES/склад | qty только в base материала |
| Отчёты / ПТО (R9) | Суммы по материалу только в одной базе; иначе запрет смешения |
| INT1 1С | Каталог ЕИ + коэффициенты — почти обязательный контракт |

## Фазы (если выбрать A, с B на документах)

1. **Каталог ЕИ + `baseUomId`**, миграция `кг`/`уп` → id; регистры без смены смысла чисел.
2. **Системные переводы внутри размерности** (ввод в г при базе кг).
3. **Альтернативы материала** (фасовка шт↔кг) + при необходимости snapshot фактора в строке (B).
4. **Явный qtyBasis в спеке** (normUom / per 1000 uom).

## Как выбирается ЕИ материала (зафиксировано)

**Источник истины — карточка материала** (`baseUomId`). Модель учёта базовую ЕИ не задаёт.

1. Обязательное поле учётной ЕИ из каталога.
2. Soft-default при создании: `продукт` → `уп`, иначе → `кг` (как seed сегодня).
3. Остаток / резерв / проводки — только в учётной ЕИ.
4. Смена учётной ЕИ после движений — жёсткая политика ([ниже](#смена-учётной-еи-после-движений)).
5. Прочие ЕИ — позже: альты / system peer / catch weight — без второго регистра.

## Привязка к модели учёта

Модель ([accounting-models](../entities/accounting-models.md)): партии, смешение, `qtyDisplayDecimals`. Базовую ЕИ на модель не вешаем; максимум soft-default. Decimals остаются в модели.

## Выбранный сценарий: одна учётная ЕИ + задел под альты

Как в SAP **Base Unit of Measure (MEINS)** / stock-keeping unit: система **управляет запасом в одной ЕИ**; всё введённое в других ЕИ пересчитывается в базу до проводки ([SAPinsider: UoM errors](https://sapinsider.org/avoid-these-11-common-unit-of-measure-errors/), material master Additional data → Units of Measure / MARM).

### Слои (сейчас vs потом)

| Слой | MVP (сейчас зафиксировать) | Позже (не ломая регистры) |
|------|----------------------------|---------------------------|
| Каталог `uoms` | да | + размерности, системные факторы кг↔г |
| `material.baseUomId` | да (вместо строки `unit`) | без смены смысла |
| Регистры `stock`, `active_reservations`, дельты | `quantity` = учётная ЕИ, **без** `uomId` в строке | не трогать схему qty |
| Документы | `quantity` в учётной (как сейчас) | опц. `qtyEntry` + `uomEntry` + snapshot factor; проводка всё равно в base |
| Альты материала | можно не делать | `altUomId` + `factorToBase` для отчётов/столов/ввода |
| Catch weight | вне MVP | см. раздел ниже; stock по-прежнему кг |

Инвариант проводки: `applyStockDelta(..., delta)` всегда в **base**. UI/отчёт может показать `qtyBase * factor` или `qtyBase / factor`.

### Нужно ли менять регистры?

Сейчас строка stock ≈ `{ materialId, lotId, warehouseId, quantity }` — ЕИ **подразумевается** материалом. Три подхода:

| Подход | Что в регистрах | Плюсы | Минусы |
|--------|-----------------|-------|--------|
| **R1. Qty-only (рекомендуем)** | Как сейчас: одно число; ЕИ = `material.baseUomId` (как SAP `MARD`←`MARA.MEINS`) | Совместимо с SAP IM; простые FEFO/reserve; альты = presentation | Смена base запрещена; «немая» строка остатка без join к материалу не самоописываема |
| **R2. Snapshot `uomId` на строке stock/движения** | Пишем `uomId` (= base на момент проводки) рядом с qty | Аудит «в какой ЕИ лежало», если base когда-то сменят ошибочно | Дубль; при легальной смене base всё равно нужна миграция чисел; путаница «uom строки ≠ base материала» |
| **R3. Dual qty в регистре** (base + secondary) | Два числа на stock | Удобны места + кг | Ломает простоту резерва/FEFO; два контура расхождений; **не берём** для выбранного сценария |

**Вывод для Vilar:** регистры **по смыслу не меняем** (R1). Меняется справочник материалов (`unit` → `baseUomId`) и слой форматирования/отчётов. При появлении альтов — **не** добавлять колонки qty в `stock`; конвертировать при чтении. Опционально позже на **журнале движений** (не на остатке) хранить entry UOM для аудита ввода — это документы/movement log, не регистр остатка.

### Плюсы / минусы выбранного пути vs альтернатив учёта

| | Одна учётная ЕИ (наш выбор) | Несколько учётных / dual stock | ЕИ только на документе, регистр «безразмерный» |
|--|-----------------------------|-------------------------------|-----------------------------------------------|
| Целостность | Высокая | Риск рассинхрона двух остатков | Низкая: нельзя суммировать историю |
| Сложность кода | Низкая | Высокая | Средняя, отчёты хрупкие |
| Гибкость UI | Через альты позже | «Нативная» в двух ЕИ | Кажется гибкой, пока не смешают кг и шт |
| Стык SAP/1С | Прямое соответствие Base UoM | Редко нужно | Плохой контракт |
| Смена ЕИ | Жёстко ограничена (как SAP) | Ещё сложнее | Хаос в истории |

### Задел под «гибкость отчётов и столов»

Без смены регистров:

1. **Presentation convert:** `formatMaterialQty(n, materialId, { uom: 'g' })` → из base.
2. **Материальные альты** с коэффициентом — колонка «в упаковках» в отчёте остатков.
3. **Предпочитаемая ЕИ показа** на материале или user preference — только UI default.
4. Ввод в альте на рабочем столе → сразу в base перед save/post.

Коэффициенты **внутри размерности** (кг↔г) — системные; **между** шт и кг — только на материале (как SAP: dimensionless / cross-dimension только per material, MARM).

## SAP: как хранят материал и количества

Упрощённая карта MM (ECC; в S/4 часть движений — `MATDOC`, смысл тот же).

### Типы таблиц / слои

| Слой | Таблицы (примеры) | Роль | ЕИ в данных |
|------|-------------------|------|-------------|
| Каталог ЕИ | `T006` (+ тексты) | Справочник единиц, размерности | сами коды ЕИ |
| Master материала | `MARA` | Клиентский уровень: тип, вес… **`MEINS` = Base UoM** (stock-keeping) | учётная ЕИ **на материале** |
| Альты / коэффициенты | `MARM` | `MEINH` + числитель/знаменатель к base | не остаток |
| Завод / склад / оценка | `MARC`, `MARD`, `MBEW` | MRP, **остаток по складе**, цена | qty в **base**; колонки вроде `LABST` **без** поля ЕИ — ЕИ из `MARA.MEINS` |
| Партия | `MCH1` / `MCHA` и сток с `CHARG` | Batch | qty снова в base |
| Документ движения | заголовок `MKPF` + строки `MSEG` (S/4: `MATDOC`) | Факт проводки | **`MENGE`+`MEINS`** (base) и часто **`ERFMG`+`ERFME`** (единица ввода); иногда order unit |
| Закупка и др. | `EKPO` и т.п. | Заказные ЕИ | свои unit fields; в запас всё равно уходит в base |

Ключевые свойства модели SAP:

1. **Остаток (`MARD` и аналоги) хранит только число в base** — отдельного `uom` на строке остатка нет; смысл числа = текущий `MARA.MEINS`.
2. **Гибкость ввода/показа** — через `MARM` и поля *unit of entry* на документе; stock UI (напр. MMBE) может *показать* альту, пересчитав от base текущим фактором.
3. На **строке материала документа** SAP **денормализует** base (`MEINS`) рядом с `MENGE` и отдельно фиксирует ввод (`ERFME`/`ERFMG`). Это аудит «что ввели» и снимок учётной ЕИ на момент проводки.
4. Смена `MEINS` после стока/зависимостей — жёстко заблокирована (см. раздел смены base).

Источники: обзоры MM tables (MARA/MARD/MARM), поля [MSEG](https://www.stechno.net/repository/sap-tables.html?id=MSEG&view=saptable) (`MENGE`/`MEINS`/`ERFMG`/`ERFME`), community про entry vs base.

### Соответствие Vilar ↔ SAP

| SAP | Vilar (сейчас / целевой R1) | Расхождение |
|-----|-----------------------------|-------------|
| `T006` | каталог `uoms` (план) | пока строка `unit` |
| `MARA.MEINS` | `material.baseUomId` (план; сейчас `unit`) | **совпадает по смыслу** |
| `MARM` | альты материала (фаза 2+) | пока нет — главный функциональный gap |
| `MARD` qty | `stock.quantity` по lot+warehouse | **совпадает:** qty без ЕИ в строке остатка |
| batch/`CHARG` | `lots` + stock по `lotId` | у нас партия сильнее в домене ОП |
| `MSEG.MENGE/MEINS` | строки документов / журнал дельт: в основном одно `quantity` | **gap:** нет снимка учётной ЕИ и пары entry на строке движения |
| `MSEG.ERFMG/ERFME` | нет | появится, когда нужен ввод в альте (вариант B) |
| `MARC`/`MBEW` | нет (нет завода/оценки MM) | вне скоупа пилота |
| Plant / storage location | `warehouses` | упрощённая модель |

**Итог по «разъезду»:** выбранный учётный подход (одна base, остаток только в ней, ЕИ на карточке материала) — **тот же класс модели, что SAP IM**. Мы не уезжаем от SAP в сторону dual-stock. Отстаём по: каталогу/альтам (`MARM`), снимку ЕИ и entry на **документе** (`MSEG`), заводской/финансовой глубине.

Диаграмма слоёв:

```text
SAP:     T006 → MARA.MEINS → MARD.qty(base only)
                └→ MARM alts
         MKPF/MSEG: MENGE+MEINS + ERFMG+ERFME

Vilar:   uoms → material.baseUomId → stock.qty(base only)     [R1 = как MARD]
                └→ alts (позже ≈ MARM)
         documents / movement log: quantity  [позже + entry ≈ MSEG]
```

## Риск: нет ЕИ в регистрах — уязвимость для развития?

Краткий ответ: **для регистра остатков — нет, это норма SAP (`MARD`)**. Риск не в «отсутствии колонки uom в stock», а в (а) смене base без запрета и (б) отсутствии снимка на **истории документов**, если когда-либо пересчитают qty или сломают join к материалу.

### Что не является уязвимостью

| Страх | Почему ок при R1 + запрете смены base |
|-------|----------------------------------------|
| «Потом не добавим альты» | Альты = master + convert при чтении; `stock` не обязан знать альту (как MMBE от `MARD`+`MARM`) |
| «Отчёты в других ЕИ» | Presentation layer: `qty × factor(now)` или factor на дату — без колонки в остатке |
| «INT1 / 1С / SAP» | Контракт «остаток в base UoM материала» — стандарт; альты отдельно |
| «FEFO/резерв усложнятся» | Наоборот: одно число, как сейчас |

Остаток без ЕИ в строке **корректен**, пока инвариант: *число в `stock` всегда в текущем `baseUomId`, а `baseUomId` не меняется при ненулевой истории* (server-side).

### Где реальные риски развития

| Риск | Суть | Митигация |
|------|------|-----------|
| **R-a. Illegal / ошибочная смена base** | Числа те же, подпись другая → ложь в отчётах | Уже: **API-запрет**; не полагаться на UI |
| **R-b. Админ-миграция ×k** | Нужно трогать все qty; без снимка ЕИ на старых доках труднее доказать «было в кг» | Либо не делать; либо миграция + audit; опц. перед миграциями — бэкап |
| **R-c. Документ без снимка MEINS** | SAP на `MSEG` пишет `MEINS`; у нас qty «немой». Пока base стабилен — join к материалу достаточен. Если появится миграция/обмен — история хуже читается offline | **Фаза документов:** при желании писать `uomBaseId` (+ позже entry) на строку документа / movement log — как `MSEG`, **не** на `stock` |
| **R-d. Смена фактора альты после проводок** | Показ «в упаковках» по *текущему* MARM врёт для старых периодов (известная оговорка SAP) | Snapshot factor на строке документа при entry; для чистого display — принять «текущий фактор» или хранить factor в отчётном срезе |
| **R-e. Dual stock «потом допилим в stock»** | Если начать писать второе qty в регистр — разъезд с SAP IM и рост сложности | Держать catch/secondary вне `stock` (партия/строка), см. FW2 |

### Рекомендация по эволюции схемы

1. **`stock` / `active_reservations`:** оставить **без** `uomId` (R1 = `MARD`-like). Это не долг и не дыра.
2. **Защита смысла числа:** серверный запрет смены `baseUomId` + чеклист.
3. **Документы — заложить контракт рано, полный UX альтов не обязателен сразу** (см. [ниже](#документы-заложить-сразу-или-потом)).
4. Не копировать в Vilar `MBEW`/заводы, пока нет оценки запасов.

**Вывод:** отсутствие ЕИ в регистрах остатка — **не уязвимость относительно SAP**; уязвимость была бы в смене base без серверного инварианта или в попытке хранить несколько независимых остатков. Для развития важен задел на строке **документа**, не dual qty в `stock`.

### Документы: заложить сразу или потом?

**Идеал по устойчивости** — при внедрении `baseUomId` сразу определить форму строки документа «по-саповски», даже если UI пока вводит только в base:

| Поле | MVP-поведение | Зачем |
|------|---------------|--------|
| `quantity` (или явное `qtyBase`) | Как сейчас: число в учётной ЕИ; проводка в `stock` | канон |
| `uomBaseId` (денорм.) | При create/post писать текущий `material.baseUomId` | аудит как `MSEG.MEINS`; история читаема без сюрпризов |
| `qtyEntry` / `uomEntry` | В MVP: `null` или копия base (`qtyEntry = quantity`, `uomEntry = uomBaseId`) | место под альты без второй миграции схемы |
| Коэффициент / snapshot | Пока не нужен; при альтах — на момент post | защита от смены factor в `MARM`-аналоге |

**Не идеал (перегруз MVP):** сразу справочник альтов, выбор ЕИ в каждой строке RCP/PRI, catch weight, пересчёт во всех столах — если бизнесу пока хватает кг/уп.

Практичный компромисс:

1. Фаза G12-a: каталог + `baseUomId` + API-запрет смены + при post **проставлять `uomBaseId`** на строке (и в movement log, если пишем дельты).
2. Поля entry зарезервировать в модели/типах (даже если UI их не показывает) **или** добавить вместе с первой альтой — дешевле, чем потом угадывать смысл старых qty.
3. Фаза G12-b: альты + ввод `uomEntry` → пересчёт в base до `applyStockDelta`.

Итого: «идеальный кейс» = **сразу дисциплина документов (снимок base; слот под entry)**, а не сразу богатый multi-UOM UI. Остатки по-прежнему без ЕИ.
## Несколько ЕИ: обзор

Инвариант: **одна базовая ЕИ остатка** на материал. «Несколько» = роли, не два независимых stock qty.

| # | Кейс | Как |
|---|------|-----|
| 1 | кг ↔ г (та же размерность) | Системный перевод |
| 2 | шт ↔ кг, **фиксированный** фактор | Alt на материале + snapshot в строке |
| 3 | Приёмка/списание в разных ЕИ ввода | Разный entry, один `qtyBase` |
| 4 | ГП `уп` + сырьё `кг` в спеке | Разные материалы + spec bridge |
| 5–7 | шт ↔ кг, **плавающий** кг | [Catch weight](#шт--кг-с-плавающим-весом-catch-weight) |
| 8 | Предпочитаемая ЕИ показа | UI-preference от базы |

**Запрет:** два остатка по одному `materialId` без жёсткой связи пересчёта.

Роли: **base** · **system peer** · **alt (fixed)** · **catch secondary** · **spec bridge**.

## шт ↔ кг с плавающим весом (catch weight)

Смысл: у «штуки» (мешок, бочка, канистра) вес **не константа** на карточе материала. 10 шт партии A ≠ 10 шт партии B в кг. Материальный `factorToBase` врёт.

Для Vilar важный якорь: спека и assay/dry — **весовые**; списание в производство логично в **кг**. Поэтому при catch weight рекомендуемая база материала = **`кг`**, а `шт` — вторичный контур (логистика / удобство), не вторая истина остатка.

### Режимы на карточке материала (флаг / профиль UOM)

| Профиль | База | шт | Пересчёт |
|---------|------|-----|----------|
| `fixed` | кг (или шт) | alt с `factorToBase` | материал / snapshot строки |
| `catch_weight` | **кг** | вторичное qty | только факт взвешивания / данные партии или строки |
| `count_only` | шт | — | без кг (упаковка без веса в учёте) |

Профиль — свойство **материала** (рядом с `baseUomId`), не модели учёта.

### Сценарные кейсы

**CW1 — Приёмка (RCP): пришло N мест, взвесили брутто/нетто**

- Оператор вводит: `qtyPcs = 40`, `qtyKg = 982.4` (или тара + нетто).
- В регистр stock: **+982.4 кг** (база).
- На партию (или строку→партию): сохранить `secondaryQtyPcs = 40` и/или `kgPerPcs` = 982.4/40 как *справочный* средний для этой партии.
- Нельзя провести только шт без кг (для `catch_weight`).

**CW2 — Остаток на экране**

- Канон: `120.5 кг` по регистру.
- Опц. показ: «≈ 5 шт» из `lot.secondaryQty` или из среднего партии — **оценка**, не второй регистр.
- Сумма шт по складу допустима как аналитика; расхождения шт vs «кг/номинал» — сигнал к INV, не автоправка кг.

**CW3 — Резерв / подбор (RES): потребность в кг**

- План и FEFO считают **кг** (как сейчас).
- «Сколько мешков взять» — подсказка: `ceil(needKg / lot.avgKgPerPc)`, подтверждение фактом в кг при отпуске.
- Резервировать «3 шт» как stock-единицу — **нет** (база кг).

**CW4 — Отпуск в производство (PRI): списали 2 мешка, на весах 48.1 кг**

- Ввод: шт (удобство) + **обязательный** факт кг (весы / подтверждение).
- Проводка: −48.1 кг; secondary на партии: −2 шт (если ведём шт на партии).
- Запрет: провести PRI только по шт с подстановкой номинала 25 кг с материала — для catch weight это скрытая ложь.

**CW5 — Отпуск «только по среднему партии» без весов**

- Допустимо как упрощение: `qtyKg = qtyPcs * lot.avgKgPerPc`, avg зафиксирован при приёмке.
- Риск: накопление ошибки; нужен периодический INV по весу.
- Политика материала: `catchWeightIssueMode = weigh_required | use_lot_average`.

**CW6 — Частичная единица (вскрыли мешок, взяли 3 кг)**

- Secondary шт либо не трогаем, либо ведём дробные шт (плохо), либо шт только для целых мест, а остаток «вскрытого» — только кг.
- Практичное правило: **шт учитываем только для целых закрытых мест**; вскрытая тара живёт в кг до обнуления. Иначе catch weight раздувается.

**CW7 — Инвентаризация (INV)**

- Считали 7 мешков, взвесили 171 кг; книга 175 кг / 7 шт.
- Корректировка регистра — по **кг** (и при необходимости secondary шт к 7).
- Расхождение «шт сходится, кг нет» — нормальный catch-weight сигнал (влажность, россыпь, ошибка среднего).

**CW8 — Перемещение (TRN)**

- Движение базы в кг; secondary шт переносится пропорционально или явно (оба поля в строке), чтобы на складе-приёмнике не потерять счёт мест.

**CW9 — Возврат / PRR / излишки**

- Те же правила: кг обязателен для stock; шт — если профиль catch и двигаем целые места.

**CW10 — Фиксированный номинал «≈25 кг» на этикетке vs факт**

- На материале можно хранить `nominalKgPerPc` **только как подсказку UI** (плейсхолдер), не как factor проводки при `catch_weight`.
- Путать с `fixed` нельзя: иначе снова тихий неверный пересчёт.

### Варианты реализации (плавающий кг)

| ID | Суть | Плюсы | Минусы |
|----|------|-------|--------|
| **FW0** | Нет catch: всегда ввод в кг; шт вне системы | Просто, стыкуется с GMP-весом | Нет контроля мест |
| **FW1** | Строка документа: оба поля `qtyKg` + `qtyPcs` обязательны при профиле; stock только кг; шт не копится | Честный вес; мало сущностей | Нет остатка «в местах» |
| **FW2** | FW1 + на **партии** `secondaryQty` (шт) и `avgKgPerPc` | Подсказки «сколько мешков»; инвентаризация мест | Нужна дисциплина частичных мешков (CW6) |
| **FW3** | Два регистра остатка (кг и шт) | Полный dual stock | Ломает простоту FEFO/резерва; для ОП избыточно |
| **FW4** | База = шт, кг атрибут партии | Удобно логистам | Плохо для спеки/assay; **не рекомендуется** в Vilar |

**Рекомендация на перспективу:** для материалов с плавающим весом — профиль `catch_weight`, база **кг**, режим **FW2** (факт кг в документах + шт на партии). Пока профиль не нужен бизнесу — **FW0** / обычный `fixed`.

Не смешивать: материал с `fixed` factor и тот же SKU как catch — разные профили (или смена профиля только без движений).

### Влияние на уже существующее

| Контур | Catch weight |
|--------|----------------|
| Спека / G7 | Без изменений: нормы и assay в кг |
| FEFO / RES | Резерв и free stock в кг; шт — UX |
| Complete / PRI | Строка факта: кг обязателен; шт опц. |
| Отчёты / R9 | Агрегаты в кг; колонка «мест» — отдельно, не суммировать с кг |
| INT1 | Часто в ERP: base + secondary UOM / catch-weight flag — заложить в контракт заранее |

### Фазирование относительно G12

1. Каталог + `baseUomId` на материале (зафиксированный канон); регистры R1.
2. System peer (кг↔г) + fixed alt (presentation / optional entry).
3. **Catch weight (FW2)** — только по подтверждённой потребности.
4. Spec bridge явный.

## Смена учётной ЕИ после движений

### Кейс

1. Материалу назначили учётную ЕИ = `кг`, провели RCP/RES/PRI, есть `stock` и история.
2. Пользователь хочет сменить на `г` или на `шт`.

### Практика SAP (ориентир)

- Base UoM = единственная stock-keeping; альтернативы в material master (MARM), order/issue/sales unit могут отличаться от base, проводка в base.
- **Смена base после транзакций почти всегда запрещена** (SAP note 138767 и проверки MM02): блокируют остаток текущего/прошлого периода, открытые PR/PO, резервы, BOM, production orders, часть SD и т.д. Типичный ответ системы: *Display errors* — список зависимостей.
- Если смена всё же допустима (нет стока и блокирующих документов) — иногда запрашивают **коэффициент пересчёта** для связанных master-данных (info records).
- Если сток/история есть — **не менять base**, а:
  - завести **alternative UoM** и использовать её как purchase/issue/display unit; или
  - завести **новый материал**, перевести остаток (transfer), старый закрыть.
- Выбор base: не слишком крупная (потеря точности из‑за округления) и не слишком мелкая (переполнение); для счётных — часто наименьшая (EA, не case). У Vilar хранение qty уже с `roundQty`/6 знаков — тот же принцип при выборе кг vs т vs г.

Источники: [SAP Community — change UoM](https://community.sap.com/t5/enterprise-resource-planning-q-a/change-unit-of-measure/qaq-p/5155645), [SAPinsider — 11 UoM errors](https://sapinsider.org/avoid-these-11-common-unit-of-measure-errors/), help/S4 «change base unit» checks.

### Политика для Vilar (предложение)

| Ситуация | Поведение |
|----------|-----------|
| Нет блокирующих зависимостей (чеклист ниже) | Разрешить смену `baseUomId` |
| Есть stock / резерв / posted-история / … | **Запрет** смены учётной ЕИ |
| Нужна другая ЕИ для ввода/отчётов | Альтернатива + коэффициент; base не трогать |
| Учётная ЕИ ошибочна, сток есть | Новый материал + перевод остатка; не «переименовать» base |
| кг→г при нулевом стоке | Обычная смена; при стоке — запрет или отдельная админ-миграция |

**Почему не «просто пересчитать» в карточке:** история уже в числах без ЕИ в строке; смена подписи врёт или требует массового ×k по всем qty. SAP блокирует по той же причине.

### Где Enforce: обязательно backend

Запрет **не** «только фронт». UI — UX (disabled field, текст ошибки). Истина — **API**.

Канон при реализации G12:

1. `PUT/PATCH` материала: в `beforeUpdate` (уже есть хук у `materials` в `backend/src/index.js`, рядом с `normalizeMaterialAccounting`) — если `baseUomId` изменился → `assertBaseUomChangeAllowed(materialId)` → иначе `400` с списком причин (аналог SAP Display errors).
2. Обход через generic CRUD / прямой вызов store из других сервисов — тот же assert, не дублировать только в React.
3. Фронт может заранее дергать тот же чеклист (опц. `GET …/base-uom-change-blockers`) для подсказки; отсутствие вызова не ослабляет защиту.
4. Админ-миграция, если появится — **отльный** privileged endpoint/скрипт с audit, не «снять disabled в форме». Обычный update материала миграцию не делает.

Иначе: DevTools / curl / будущий INT1 спокойно перепишут `baseUomId` при живом остатке — целостность qty сломана. Это не «дыра auth», а **целостность домена**; чинится серверным инвариантом, как уникальность серии и guards статусов.

Чеклист блокировок (сервер считает, минимум):

- `stock` по партиям материала;
- `active_reservations`;
- posted документы со строками материала;
- спецификации / заказы с qty;
- (позже) черновики — по выбранной строгости.

Текст ошибки API ≈: «Учётную ЕИ нельзя изменить: есть движения/остаток. …»

### Админ-миграция (исключение)

Не через карточку. Явная операция + коэффициент + пересчёт qty + audit. На пилот можно не делать.

## Открытые вопросы

1. Какие ЕИ на пилоте кроме кг/уп?
2. Нужен ли MVP сразу только `baseUomId` без альтов (альты — фаза 2)?
3. Catch weight / счёт мест — нужен на пилоте или FW0?
4. Строгость блокировки смены base: запрет при **любой** истории документов или только при ненулевом stock?
5. Нормы спеки — только масса на уп ГП?
6. Делать ли админ-миграцию кг↔г или сразу политика «только новый материал»?

## Рекомендация (сводка)

- Одна **учётная** ЕИ на карточке материала; остаток как SAP `MARD`: qty без ЕИ в строке (**R1**).
- Нет ЕИ в `stock` — **не** архитектурная уязвимость vs SAP; риск закрывается API-запретом смены base; при альтах — снимок entry/base на **документе** (как `MSEG`), не dual qty в остатке.
- Альты ≈ `MARM` — фаза 2+ без ломки регистров.
- Смена учётной ЕИ после движений — **запрет на API**; UI только отражает.
- Catch weight / FW2 — отдельно; не dual stock.
- Не D/E.
