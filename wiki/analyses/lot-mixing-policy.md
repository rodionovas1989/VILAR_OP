# Analysis: политика смешения партий сырья

**Статус:** только разбор, в коде не реализовано. Сейчас жёстко [одна партия на компонент](../concepts/gmp-one-lot-per-component.md). ROADMAP G1.

**Не путать с [D010](../decisions/D010-same-lot-multi-warehouse.md):** одна и та же партия на нескольких складах — это не смешение партий.

## Зачем

GMP по умолчанию: в одной серии ГП на компонент спецификации — одна партия. На деле SOP предприятия может разрешать:

1. смешение партий **одного производителя** (типично вспомогательные вещества, растворители);
2. **валидированное** смешение партий **разных производителей** (отдельная процедура, однородность, срок смеси по самой ранней дате — GMP ЕАЭС 8.4).

Обе схемы требуют **нескольких строк** `(материал, партия, склад, qty)` на одну позицию спецификации: подбор, RES, факт, PRI.

## Где хранить настройку

Оси разные: шаблон номера / sequence (уже в модели учёта) и правило потребления партий. Не плодить чекбокс на каждом материале и не строить платформу «блоков настроек».

**Канон для реализации:** поле на **модели учёта** (`lotMixPolicy`), материал по-прежнему только `accountingModelId`.

| Значение | Смысл |
|----------|--------|
| `single` | как сейчас: одна партия на позицию спеки (дефолт сидов) |
| `sameManufacturer` | несколько партий одного `lots.manufacturerId` |
| `validated` | несколько партий, в т.ч. разные производители; «валидировано» — допущение процесса, не отдельный документ в v1 |

Позже, если понадобится исключение на одну рецептуру: override на **строке спецификации**. Не закладывать сейчас.

Не класть политику в админ-флаг всей системы: у закупа и у собственного АФС правила разные, это класс материала.

## Что ломается в процессе (обязательный контур)

Сейчас инвариант «1 specLine → 1 pick / 1 lot»:

- подбор: `suggestPicksForOrder` берёт первую партию с `free >= need`, иначе ошибка «смешивание запрещено»;
- подтверждение: `confirmMaterialPicks` — уникальность `specLineId` и «материал → одна партия»;
- UI подбора и факта — одна строка на компонент;
- RES/PRI уже умеют **N строк** и **N документов по складам** — складской контур готов.

При политике ≠ `single`:

1. **Подбор** режет need по FEFO/FIFO (и sequence) на несколько партий; фильтр производителя для `sameManufacturer`.
2. **ТЧ** — несколько строк с одним `specLineId` (ключ строки: specLine + lot + warehouse).
3. **Резерв / факт / complete** — те же N строк; срок смеси для предупреждений — `min(expiryDate)` входящих партий.
4. По-прежнему нельзя смешать **базовый материал и аналог** в одной позиции спеки.
5. Пакетный подбор: виртуальный claimed остаётся по `lotId×склад`, но один заказ может занять несколько партий.

## Не делать в первой нарезке

Отдельный документ «акт смешения», авто-создание промежуточной «смешанной партии», смешение как складская операция вне заказа. Сначала — несколько лотовых строк в заказе под явной политикой модели.
