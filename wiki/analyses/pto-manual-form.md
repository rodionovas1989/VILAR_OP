# Analysis: производственно-технический отчёт (ручная форма)

Источник: фото заполненного бланка «Производственно-технический отчёт на производство», Фармцентр ВИЛАР, февраль 2011 (участок переработки; продукт по рукописи читается неуверенно).

Назначение: состав/логика бумажного ПТО + разбор цифр блока движения сырья + архитектурные блокеры OP для аналога в системе. Канон кода не меняет.

## Шапка

Один бланк = один участок × один календарный месяц. Подпись внизу.

## Блоки 1–2 (кратко)

1. **Программа** — план/факт/остатки ГП; на образце заполнена строка «сдано»: **65 кг** за месяц, **110 кг** с начала года.
2. **Показатели** — стадии, машино-часы, простои; на образце пусто.

Дальше — только блок 3.

---

## Блок 3. Движение сырья: колонки и формулы

Группы колонок: остаток начало (всего / в сырье / в НЗП) → приход → остаток конец (те же разрезы) → расход на пр-во (**загружено**; часто ещё пересчёт на 100%) → расход на выработку (месяц + YTD) → расход на ед. (норма / факт месяц / факт YTD) → отклонение ±.

Суммовые колонки на бланке есть, на образце не ведутся. На заполненных строках «всего» ≈ «в НЗП», «в сырье» пусто — весь остаток учтён как цеховой.

### Рабочие уравнения

1. **Складской баланс (если приход сразу в том же контуре, что расход):**  
   `остаток_нач + приход − расход_на_выработку_мес ≈ остаток_кон`
2. **НЗП / загрузка (точнее для цеха):**  
   `НЗП_нач + загружено − расход_на_выработку_мес ≈ НЗП_кон`  
   Когда `загружено = приход` и остаток только в НЗП, (1) и (2) совпадают.
3. **Удельный факт:**  
   `факт_мес ≈ расход_мес / сдано_ГП` (здесь сдано = **65**).  
   `факт_YTD ≈ расход_YTD / сдано_YTD` (здесь **110**), где совпадает.
4. **Отклонение** (если заполняют): факт − норма или (факт−норма)×выпуск — на образце почти не читается.

«Загружено» и «расход на выработку» — **разные** величины: загрузили в процесс ≠ списали на готовую выработку месяца (возврат растворителя, остаток в аппарате, переходящее НЗП).

### Выводы по заполнению

1. **Основной баланс**, которым реально пользуются: остаток и расход на выработку; «загружено» часто копирует приход.
2. **Спирт** — единственная явная развилка приход≠загружено (−200). Уравнение НЗП через **загружено** закрывается; итоговый «всего» на конец **не** включает эти 200 (ошибка бланка **или** списание/возврат вне колонок **или** остаток «в сырье» не проставили).
3. **Хлороформ** — одновременно не сходится баланс и не сходится факт÷65; с высокой вероятностью **ошибка цифр на бланке или наше чтение**.
4. **Желатин, бензалконий** — баланс по расходу ок, но «факт на ед.» не равен расход/65 (у желатина факт=норма). Ручной перенос нормы или другая база выпуска.
5. **YTD**: для гидрозатвора и угля расход YTD ≈ 2× месяц при сдаче 110≈65+45 — согласовано с двумя месяцами; для этилацетата факт YTD=5 при 650/110≈5,9 — слабое место.
6. Растворители (спирт, хлороформ) в живом учёте часто имеют **регенерацию/возврат** — бумажная форма это плохо моделирует одной колонкой «расход».

## Архитектурные особенности OP, мешающие такому отчёту

Допущение пользователя: появится **промежуточный склад производства** между сырьём и СГП; TRN сырьё→пр-во будут явными. Ниже — что всё равно мешает или нужно заранее решить.

### Высокая критичность

| Тема | Сейчас в OP | Почему ломает ПТО |
|------|-------------|-------------------|
| **Нет склада-приёмника у PRI** | `postProductionIssue` = write-off: остаток уничтожается, движения только `issue` ([documents.js](../../backend/src/services/documents.js)) | «В НЗП» как остаток **не существует**. Промежуточный склад чинит картину **до** списания: остаток на пр. складе ≈ «в НЗП» / «у цеха»; PRI с пр. склада ≈ «расход на выработку». Нужна жёсткая конвенция: когда TRN, когда PRI. |
| **Нет исторических срезов остатка** | `stock` — только текущее | Остаток на начало/конец месяца = реконструкция из `material_movements` (или отдельные snapshot’ы). Ошибочные/поздние перепроведения ломают ретроспективу. |
| **Дата периода** | В журнал пишется `at` = время проведения; у документа есть `date` | Отчёт «февраль» по `at` ≠ по учётной `date`. **Канон (R10 / D013):** срезы по `postingDate` (≈ BUDAT), не по `at`. |
| **Знаменатель «на ед. продукции»** | Выпуск — PRR/заказ/серия; несколько продуктов на одном РЦ | ПТО — один продукт на бланке. Факт/норма на ед. требуют явного **фильтра продукта (и базы: кг сдачи vs серии)**; иначе удельные расходы бессмысленны. |
| **Норма** | Спека: `qtyPerUnit` на **1000 уп.** + пересчёт assay/dry ([lot-recalc](../concepts/lot-recalc-assay-dry.md)); G2b «этапы и нормы техкарт» — идея | Бумажная «норма на ед.» ≠ сырой `qtyPerUnit` без перевода и без фиксации, какую норму показывать (плановая до assay vs после). |

### Средняя

| Тема | Смысл |
|------|--------|
| **Загружено vs расход** | Появятся только если TRN на пр. склад ≠ PRI. Пока complete атомарно делает PRI+PRR — различить нельзя. RES остаток не двигает. |
| **Привязка цеха** | `workCenterId` есть у заказа и `production_register`, **нет** у строки `stock` / обязательной связи склад↔РЦ | Разрез «как на бланке по участку» = договориться: пр. склад = цех, или фильтр через заказы/регистр. |
| **Партии** | Остатки и движения — lot×warehouse | ПТО — материал без партий; отчёт должен **сворачивать** лоты (и решить, показывать ли %). |
| **Аналоги** | Факт может быть с materialId ≠ строки спеки | Норма и факт стыковать по **слоту спеки**, не только по materialId. |
| **Полуфабрикаты** | Тип материала есть; отдельного маршрута НЗП-стадий нет | Многостадийный полупродукт на бланке = отдельные материалы/склады/заказы, не одна колонка «в незав.». |
| **Возврат растворителей** | Нет отдельного сценария «регенерация» | Как у спирта на бланке: нужны обратные движения (TRN/RCP/корректировка), иначе баланс месяца разъедется. |

### Ниже / решаемо отчётом

- Агрегация YTD с 1 января по тем же правилам, что месяц.
- Суммы/рубли — в OP нет себестоимости на движениях (колонки можно не делать).
- `% содержания` на бланке — ближе к LCH/assay, не к складу.
- Мультисклад PRI (D009): несколько документов на заказ — для суммы расхода не мешает, если фильтр складов/цеха задан.
- `production_register` параллелен складу: для удельных расходов удобен (есть РЦ, серия), но **остатки** только из `stock` + `material_movements`.

### Удачное целевое отображение (если есть пр. склад)

| Колонка ПТО | Кандидат в OP |
|-------------|---------------|
| В сырье | Остаток на складе(ах) сырья |
| В НЗП / у цеха | Остаток на промежуточном складе производства |
| Приход | Вход на контур отчёта (RCP на сырьё и/или TRN на пр. склад — **нужно выбрать**) |
| Загружено | TRN сырьё → пр. склад за период |
| Расход на выработку | PRI с пр. склада (или issue в `production_register`) |
| Сдано ГП (знаменатель) | PRR / отчёт выпущенных серий за период |
| Норма | Спека × перевод в «на 1 кг/уп. сдачи» |
| Факт на ед. | расход / сдано |

Открытый продуктовый выбор: считать ли «приход» приходом на **сырьевой** склад или на **цеховой**; от этого зависят уравнения (1) vs (2).

## Срезы остатка «на дату» — варианты (предварительно)

Для колонок «остаток на начало/конец» текущего `stock` недостаточно. Кандидаты (не решение ADR):

| Подход | Суть | Плюсы | Минусы / когда |
|--------|------|-------|----------------|
| **A. Накат журнала** | `остаток(D) = Σ material_movements` до границы периода (по канону `date` или `at`) | Нет новых сущностей; уже есть журнал | Тяжелее на росте данных; чувствителен к поздним cancel/repost; нужна чёткая граница периода |
| **B. Периодический snapshot** | Ночная/месячная фиксация `lot×warehouse→qty` (и опц. качество) | Быстрый отчёт «на 1-е»; аудируемый закрытый месяц | Job + хранение; дыры, если snapshot пропущен; backdated docs требуют пересчёта |
| **C. Snapshot + дельты** | Ближайший снимок + накат движений до даты | Компромисс скорости и гибкости «на любой день» | Сложнее код; всё равно канон даты |
| **D. Closing balance как документ** | Явное «закрытие месяца» (инвентаризация/ведомость) | Совпадает с бумажной дисциплиной; спорные остатки зафиксированы | Процессный overhead; не заменяет оперативный отчёт |

Для пилота OP с sqlite и умеренным объёмом движений **разумный старт — A** (возможно с кэшем агрегатов), с каноном **`postingDate`** ([R10](../../docs/plans/storno-stock-documents.md)). **B/C** — когда ПТО станет регулярным закрытием. **D** — если нужно «подписывать» остаток НЗП.

Общее: в модели сторно-документа (R10) в сумму входят движения **исходника и сторно** по `postingDate` (не «выбросить cancelled»). Закрытие периода — отдельно.
