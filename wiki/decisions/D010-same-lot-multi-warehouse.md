# D010 — Одна партия на нескольких складах (отложено)

**Контекст:** GMP требует **одну партию** сырья на компонент серии ([gmp-one-lot-per-component](../concepts/gmp-one-lot-per-component.md)). Физически одна партия может лежать на **нескольких складах**. Потребность одной строкой «материал → партия» при нехватке на одном складе нельзя закрыть без либо смешения партий (запрещено), либо разбиения по местам хранения / консолидации.

**Как сейчас (после D009):**

- Подбор и резерв смотрят `freeQty` **на выбранном складе**, не суммируют остаток партии по всем складам.
- На позицию спецификации — **одна** строка подбора; две строки на одну позицию (даже с одним `lotId` и разными складами) отклоняются.
- N RES/PRI — когда **разные** позиции заказа списываются с разных складов, а не когда одна позиция «размазана» по складам.
- Итог: партия 10+10 на двух складах при потребности 15 → подбор/резерв **не проходят**, хотя GMP «одна партия» не нарушался бы.

**Промежуточное решение (зафиксировано 2026-08-26):**  
консолидировать остаток партии на нужный склад документом **TRN (перемещение)** до резерва. Авто-разбиение потребности одной партии по складам **не делаем**.

**Идеи на потом (если операционка TRN окажется узкой):**

| Вариант | Суть |
|---------|------|
| A. Авто-аллокация | В UI одна партия; бэкенд режет qty по складам → несколько строк заказа / N RES с одним `lotId` |
| B. TRN (текущий путь) | Сначала перемещение на один склад, затем резерв |
| C. Ручной split | Явно две строки подбора с одним `lotId` и разными складами (ослабить валидацию «одна строка на specLine», оставить запрет разных lot) |
| D. Логический склад | Резерв «виртуально», физика отдельно — слабо стыкуется с текущим движком |

Предпочтительный кандидат при возврате к задаче: **A** (или **C**); смешивание **разных партий** по-прежнему вне scope.

**Не путать с D009:** D009 — разные материалы/строки с разных складов → N документов. D010 — одна позиция / одна партия, остаток разнесён по складам.
